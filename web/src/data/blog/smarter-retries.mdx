In complex systems, failures are not exceptional. They are routine. Network requests time out. DNS resolution fails. Downstream services become temporarily unavailable. Often, these disruptions are short and stop without intervention. You cannot prevent them fully. What matters is how your system reacts when they occur.

A common reaction is to retry. It seems simple: if something fails, try again. But a retry is more than a reaction. It is a strategy. You can execute a strategy well or badly.

Badly designed retries can overload healthy services and use unnecessary resources. They can change minor issues into major incidents. I have seen this in production.

In one system, a downstream API failed for only a few seconds. Clients started to retry, all with the same short, fixed delay. They all retried at the same moment, again and again, in sync. A short disruption became a long outage. The clients did not help the service recover. They kept it down.

## Exponential backoff
Advanced retry techniques start with the basic concept of exponential backoff.

Exponential backoff is a retry strategy where the delay between attempts increases over time. For example, you retry after 1 second, then 2 seconds, then 4 seconds, and so on. The goal is to give a failing service or connection more time to recover before each new attempt.

It works because most transient failures behave this way. A broken system does not usually recover immediately. It needs time. Exponential backoff puts that time into the retry policy.

But exponential backoff alone is not sufficient.

## The thundering herd
Thousands of clients can retry the same request at the same intervals. Even if those intervals increase, the retries still occur in coordinated bursts. These synchronized requests can overload the target system, especially if it is already recovering from stress. This pattern is the thundering herd problem.

To prevent this, add randomness to your retry intervals. This randomness is called **jitter**. One client waits 1.7 seconds before the next attempt, and another waits 2.3 seconds, instead of exactly 2 seconds. Jitter spreads the retry traffic across time. It decreases the chance that a flood of requests arrives at the same moment.

Jitter in exponential backoff is not an optional optimization. It is essential. Without it, your retries can amplify a failure in sync.

## Listen when the server says wait
Systems do not always fail silently. Sometimes they tell you what is wrong and what to do next.

An example is HTTP 429, the “Too Many Requests” status code. A 429 response means more than “stop.” It often includes a Retry-After header that tells you when you can safely try again.

A client that ignores this behaves badly. If your code retries immediately after a 429, it does not respect the rate limits of the service. The service asked you to pause, and you send more requests. Good retry logic listens. It adapts to what the system tells you, not only to what your code wants to do next.

## Where retries went wrong
Retries are not only for APIs with rate limits. They are critical in many real-world situations.

### Network instability
In one system, DNS resolution failures occurred at random times. They usually stopped in less than ten seconds. But the retry logic sent requests to the resolver very rapidly. The DNS service was not the problem. The retry loop was. Backoff and jitter stabilized the system immediately.

### Serverless cold starts
After we deployed new Lambda functions, every client hit the same cold path at the same time. The retry logic had no delay and no jitter. So it started a wave of retries before the functions could initialize. The functions failed because of overload during startup, not because of bugs. Slower, random retries solved the problem.

### Distributed locking
In another project, services used Redis for distributed locking. When a client did not get a lock, it retried in a fixed loop. Every few seconds, all the clients that did not get the lock hit the Redis server at once. Jitter stopped the cycle. It did not make retries slower. It made them smarter.

### CI/CD pipelines
Sometimes a build step failed because an artifact repository was temporarily out of sync. A simple retry helped, but only if it gave the repository enough time to recover. Fixed intervals failed again and again. Exponential backoff with jitter gave the mirror time to catch up. The pipeline did not stop, and no compute was wasted.

### Database failover
Failover events in a clustered database system take time. After the primary node fails, a replica can need several seconds to become the new primary. Aggressive client retries during that time only add load to a system that is trying to recover. We saw this ourselves. Waiting was not enough. The solution was to wait longer with each attempt and to not retry in sync.

## Separate the trigger from the delay
In many systems, developers write retry logic as an afterthought: a `catch` block with a hardcoded loop and a `sleep`. That can pass local testing, but it fails in production.

A better approach is to separate what triggers a retry from how long you wait between attempts. Do not hardcode these two decisions together. You can retry for some errors and not for others. You can start with exponential backoff and then change to a fixed delay. You can also use a `Retry-After` header when it is available.

When these parts are modular, you can combine policies. You can adapt to new failure modes without a rewrite of your logic. You can tune systems based on observation, not guesses.

Retries are more than error recovery. They are control flow. When used badly, they cause system instability, wasted compute, and long downtime.

Smarter retries start with exponential backoff. They improve with jitter. They become mature when they listen to status codes, headers, and what the system tells them.

Do not treat retry logic as boilerplate. It is a critical part of the resilience of your application. It needs careful design.  

Think back to the outage at the start of this post, where the clients kept a failed API down. When you build retries well, they do the opposite: they help the system recover instead of causing damage.
