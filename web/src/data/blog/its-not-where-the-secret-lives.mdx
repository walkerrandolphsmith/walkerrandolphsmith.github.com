This is the fifth post in a series about designs the constraints forced on us, and it's the one that ties the other four together. The TLS pipeline ended with "the only secret in the system is the certificate itself." The image promotion design leaned on credential-less cross-tenant federation. The GitOps machine identity was "a smaller secret, not no secret." The monorepo migration closed a token leak by switching a Dockerfile from `ENV` to a build-time secret mount. Four posts, four instances of one idea I never named. This post names it.

It starts with a question a junior engineer asked me, and it was a good one:

> "If only a handful of identities can even reach the cluster, and the app needs the credential to do its job anyway — why does it actually matter that the secret is on disk?"

That question is more correct than it sounds, and the usual answer — "because, security" — is worthless. The real answer is that the engineer was measuring secret safety with a single ruler, and there are three.

## The ladder everyone climbs (and stops too early on)

Most teams' secrets story is a maturity ladder, and it's a real one. The rungs go like this.

**Rung zero: the secret is in the repo.** Plaintext in a config file, a `.env` checked in "temporarily," a connection string in a pipeline YAML. Anyone with read access to the repo has it — which is more people than you think, and it's also every fork, every clone on a laptop, every CI cache, and every backup. The vicious part is permanence: git history is immutable, so the secret isn't leaked *until you rotate it* — it's leaked *forever*. Rotating doesn't un-commit it; `git log -p` resurrects it from any point in history. A secret that ever touched a repo must be treated as burned.

**Rung one: the secret is an environment variable.** Now it's gated by who can reach the compute — a smaller set, behind network and auth. This feels like arrival, and it's where the junior's question lives. But a static value in a process environment is readable from more places than "people with a shell": it's in `/proc/<pid>/environ`, in `docker inspect`, in a crash dump, in an APM agent that helpfully captures the environment, in one careless `logger.debug(process.env)`, in a stack trace rendered to an error page — and if it was baked at build time, it's in an image layer that outlives the container entirely. (That last one is exactly the leak I described in [the monorepo migration post](/blog/the-cutover-is-a-content-move): a feed token passed as `ENV` persisting in `docker history` for anyone who pulls the image.)

**Rung two: the secret is fetched from a store at runtime.** The app pulls it from a secret store into memory when it starts, gated by authorization and network, never written to disk, gone when the process dies. This is genuinely better, and it's where a lot of mature teams plant their flag and call it done.

Here's my claim: that ladder is real, worth climbing, and measuring the wrong thing. Every rung on it is about **where the secret lives**. Location is one dial. There are three.

## The three dials

Stop thinking about secret safety as a place and start thinking about it as three independent properties you can turn up or down:

1. **Exposure surface** — how many places the value exists, and how many things can read it. The git → env → runtime-store ladder is entirely this dial. It's a good dial. It is not the only one.
2. **Lifespan** — how long a *leaked copy* stays valid. A secret you rotate yearly has a one-year lifespan: steal it in January, use it until December. A token that expires in an hour has a one-hour lifespan. This dial is completely independent of where the secret is stored — a static API key in a perfectly secured Key Vault still has a terrible lifespan the moment a copy escapes.
3. **Blast radius and attribution** — what the credential grants when used, and whether its use ties back to a named identity. A bearer secret grants its full scope to *anyone* who presents it, and the request looks identical no matter who made it. An identity-bound credential grants only what that identity's RBAC allows, and every use is attributable to it.

The reframe that matters for a senior engineer: **you can be on rung two — Key Vault, runtime fetch, in-memory only — and still have all three dials in a bad place**, if what you fetched is a static, broadly-scoped, bearer secret. "We put it in the vault" turns exactly one dial. Teams that stop there have a beautifully stored credential that still lives a year and opens everything. The vault is the floor, not the ceiling.

| Where it lives | Exposure surface | Lifespan | Attribution / blast radius |
|---|---|---|---|
| In git | Everyone with repo history, forever | Effectively infinite | Anonymous; broad |
| In an env var | Anything that can read the process/host | Static (manual rotation) | Anonymous; broad |
| In a store, fetched at runtime | Authorized callers + the running process | Static, but re-fetchable | Anonymous bearer; scoped to the secret |
| Short-lived token minted at runtime | The process, briefly | Minutes to an hour | Bearer, but self-expiring |
| Managed / workload identity | No retrievable secret at all | Token lifetime; auto-rotated | Bound to an identity; RBAC-scoped; attributable |

Read that table top to bottom and you'll notice the ladder everyone climbs only moves you down the first column. The real maturity is moving *right*.

## Now the junior's question has a real answer

Why does a secret on disk matter if the compute is already locked down?

Because the network boundary turns exactly one dial — exposure surface — and does nothing for the other two. A static secret on disk is a **portable, durable, identity-less capability**. "Hard to get in" and "safe once something gets in" are different properties, and the on-disk static secret quietly assumes the first guarantees the second. It doesn't.

Defense in depth means assuming a layer fails and asking what the *next* layer costs the attacker. So assume something gets in by a path the network never modeled — a container escape, a server-side request forgery that makes your app fetch an attacker URL, a poisoned dependency in your supply chain, a path traversal, a logged environment, a stolen volume snapshot, a backup restored into a less-guarded environment. Now compare what the attacker walks away with:

- **Static secret on disk:** they read a file or an env var and exfiltrate a credential that works *from anywhere*, *for as long as it's valid* (a year?), *as nobody in particular*. The breach ends; the credential keeps working. They didn't get access to your box — they got the keys, and the keys travel.
- **Short-lived, in-memory, identity-bound token:** they get a credential that's gone when the process restarts, expires in minutes, can't be presented from outside the workload's identity context, and names them in the audit log if they try. The blast is contained to the breach window and attributable.

That's the whole answer. The compute boundary reduces *the probability of getting in*. It does nothing about *the value of what you steal once you do*. A secret on disk maximizes that value. The junior was right that the network shrinks the attack surface — and wrong that shrinking it is the same as making the secret safe to leave lying around. Those are two different dials, and you have to turn both.

## Secretless: turning the blast-radius dial all the way

The far-right column of that table is the goal, and it has a name: don't hold a secret at all. Replace *a credential you store* with *an identity the platform vouches for*.

In Azure, this is a managed identity. The application authenticates to Key Vault, storage, a database, a config store — using its assigned identity, with no secret anywhere in the picture:

```csharp
// No secret. The platform mints a token bound to this workload's identity;
// RBAC on the target resource decides what that identity may do.
var credential = new DefaultAzureCredential();
var client = new SecretClient(new Uri(vaultUri), credential);
```

There is no string to store, leak, or rotate. The token is short-lived and auto-renewed, it's scoped by RBAC to exactly what that identity is granted, and every access is attributable to the identity rather than to "whoever had the key." All three dials at once: zero exposure surface (nothing retrievable to expose), minimal lifespan (token, not key), minimal blast radius (RBAC-scoped and named). This is why the [TLS pipeline](/blog/the-certificate-is-an-interface) could end with "the only secret is the cert" — cert-manager authenticated to DNS with workload identity, External Secrets authenticated to Key Vault with workload identity, nothing held a credential.

When the platform can't give you pure identity, the next-best move is to make the secret *mint* short-lived tokens instead of *being* the credential that travels. That's the [GitHub App](/blog/the-cluster-pulls-because-nothing-may-push): a static private key, yes — but it never leaves as a bearer credential. It signs a JWT that's exchanged for a one-hour installation token. The key is a *signing* secret, not an *access* secret. "A smaller secret, not no secret" is precisely a statement about dials: the exposure surface is still a stored key, but the lifespan of anything that escapes the boundary is an hour, and that changes the threat model entirely.

So here's a rule worth internalizing, because a senior reviewer will hold you to it: **if you're holding a static secret for a system that supports identity, that secret is a smell, not a requirement.** Azure resource? Managed identity. On-prem or another cloud's compute that you control? It can be Arc-enabled or federated, and a static credential there means you skipped the secretless path that exists. Your own services talking to each other? mTLS or workload identity, not a shared API key. In all of these, the counterparty speaks identity, so a stored secret is a choice — usually the wrong one.

## The secret you genuinely can't get rid of

Now the honest part, because every post in this series has one, and because I want to head off the most predictable senior-engineer reaction to everything above — *"sure, but in the real world you still have API keys."* You do. The question is which ones are real.

The self-inflicted secrets I just described — for systems that support identity — are not the irreducible ones. The genuinely irreducible secret is the one where **the other side of the boundary doesn't speak identity at all.**

Concretely: your app sends SMS through Twilio, or stores objects in Wasabi. Twilio authenticates you with an Account SID and a static Auth Token. Wasabi gives you an S3-style access key ID and secret access key. These vendors do not offer federated workload identity, OIDC token exchange, or anything you can hand a managed identity to. There is no `DefaultAzureCredential` for Twilio. You cannot Arc your way out of it, you cannot mTLS your way out of it, and a reviewer who says "just federate it" is wrong — **you cannot federate what the counterparty doesn't implement.** The control isn't on your side of the wire.

This is the distinction that keeps the whole model honest. The maturity goal was never "zero secrets," because zero is not reachable when a third party hands you a static key and offers nothing else. The goal is: **eliminate every secret you're holding by choice, and for the few that are genuinely irreducible, turn the other two dials as hard as the vendor allows.**

For an irreducible third-party key, that means:

- **Never in git, never in an env var baked at build, never on disk.** Store-only, fetched at runtime into memory — the same rung-two discipline, now for the credential that actually needs it.
- **Shortest rotation the vendor supports,** automated. If Twilio or Wasabi lets you hold two active keys, you can rotate with zero downtime on a tight cadence; do it, because lifespan is the one dial you *can* still turn on a static key.
- **Narrowest scope the vendor offers.** A Wasabi key scoped to one bucket with one set of permissions has a smaller blast radius than a root key, even though both are static bearer secrets.
- **Broker it, so the static key has a blast radius of one component.** This is the move most teams miss. The general workload should not hold the Twilio token. A single, small notification service holds it — fetched at runtime, nothing else in that pod — and every other service asks *that* service to send a message, authenticated by its own managed identity. Now the irreducible secret exists in exactly one narrow place, and access to *using* it is gated by your identity plane even though the secret itself can't be. You've wrapped an identity-less capability in an identity-aware boundary.

That last pattern is the reconciliation: you can't make the vendor's key short-lived or identity-bound, but you *can* make the only thing that can reach it a workload that is. The static secret survives; its blast radius collapses to one component fronted by the same identity model as everything else.

## One more thing: the dials describe the whole lifecycle, not the storage

A closing trap, because it's where rung-two teams still get burned. The three dials are properties of the *entire life of the value*, not just where it's parked. A secret can be fetched perfectly from the store into memory and still be logged on the next line, echoed into an exception, returned in a debug endpoint, or — the build-time classic — baked into an image layer because someone used `ENV SECRET=...` instead of a `--mount=type=secret`. Where the secret is stored is the *beginning* of the question. Where it flows, what observes it, and what persists a copy is the rest of it. Turn the dials across the whole path or you haven't turned them.

## The takeaway

If I could give the junior engineer — and most teams — one mental model, it's this: stop asking *where* the secret lives and start asking what its exposure surface, lifespan, and blast radius are, end to end.

1. **Get secrets out of git and env, into a store, fetched at runtime.** This is real and necessary — but know that it only turns the exposure dial. Don't mistake the floor for the ceiling.
2. **Prefer an identity over a secret wherever the counterparty speaks identity.** Managed identity, workload identity, mTLS. A stored secret for an identity-aware system is a smell, and turning all three dials at once is the reason secretless wins.
3. **When you must hold a secret, make it mint short-lived tokens rather than be one.** A signing key with an hour-long token beats a bearer credential with a year-long life, even at the same exposure surface.
4. **Accept that some secrets are irreducible** — the third party that only issues static API keys — and stop pretending otherwise. Then turn the dials you still control: store-only, shortest rotation, narrowest scope.
5. **Broker the irreducible ones** so a single identity-fronted component holds the static key and nothing else can reach it. Wrap the identity-less capability in an identity-aware boundary.
6. **Mind the whole path.** Logs, traces, error pages, crash dumps, and image layers undo good storage. The dials are lifecycle properties, not storage properties.

The reason a secret on disk is still a problem behind a tight network is that the network only ever turned one of the three dials — and the attacker, once in, cares far more about the other two. Maturity is turning all three, eliminating every secret you hold by choice, and being honest about the handful you don't.
