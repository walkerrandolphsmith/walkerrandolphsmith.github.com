We cut content publication latency by 99% when we replaced TTL-based cache expiry with events that invalidate each cache at the moment content is published.

We built our content platform for very large scale. It serves content across mobile apps, websites, and smart devices, to 2 billion customers and billions of requests per month.
We used layers of caching: memory caches for speed, a CDN for global reach, and edge caches to reduce backend calls.
On paper, this was a textbook system for low-latency, high-availability delivery.

But something was wrong.

## The Problem No One Wanted to Own

Authors clicked “publish,” but their changes did not go live immediately.
The content appeared slowly, in some places but not in others. Some teams manage security, compliance, breaking news, or personalized experiences. For them, this delay was more than an annoyance. It was a risk.
We found that the problem was not in one layer. Multiple layers each applied their own cache policies, and the delays added up.

The CDN cached content for 30 minutes, and the backend layer did the same. As a result, content could stay stale for up to 60 minutes.
We tried shorter TTLs, but they caused new problems: higher backend load, more cache churn, and lower performance. We had optimized for scale, but we lost freshness.

## Publishing is an event

We asked: what if cache invalidation was intentional, not reactive?

We changed how we thought about the problem. TTLs only guess when content is outdated. Instead, we could send a signal at the moment that the content changed.

This idea was not new. We used event-driven architecture in other parts of our stack. But this time, we applied it to publishing.

## Versioned publish events

We added a lightweight event system. It published a message each time someone saved, reviewed, or published content. The messages were not arbitrary payloads. They were type-safe, versioned message contracts, distributed through NuGet and NPM packages.

When an author saved a draft or published a revision, the system sent an event. The event included metadata such as the content ID, revision ID, locale, content type, and the action, for example “Published.” Teams could consume these messages and invalidate their caches proactively.

We standardized the contract and supplied shared libraries. Product teams could then connect to these events easily, without writing their own logic.

### Stack Details

Azure Service Bus topics delivered our message events. For consumers, we published lightweight client libraries in NuGet (for C# services) and NPM (for Node.js apps). The libraries included the message contracts for type safety.

The cache layers were Akamai at the CDN edge, Redis for the regional application cache, and an in-memory LRU cache for hot-path read performance. We did not remove these layers. We built targeted invalidation pipelines that used the event signals.

## From an hour to seconds

The effect was immediate. Perceived staleness decreased from about 1 hour to **less than 5 seconds** in most critical paths. Content authors trusted the publish button again. Teams no longer had to choose between fresh content and fast performance, and the cache layers stayed in place. We only coordinated them better.

This change increased trust, not only throughput.

## A second use for the events

We did not expect this system to have a second use.

Each content event had a timestamp and was traceable. So we could use these messages as the base for event sourcing patterns. Teams started to build real-time projections of publishing activity. Editors could see dashboards of what was published, by whom, and when. The event stream supplied review queues that showed authors what needed attention. Auditing and compliance workflows no longer needed custom integrations, because they subscribed to the stream.

While we fixed staleness, we also created a reliable source of truth for publishing state. The cache invalidation infrastructure also enabled cross-team reporting, workflow tools, and operational insights.

## The Hardest Part Wasn’t the Code

Technically, the event system was simple to build: event stream, event store, message schemas, and client libraries.

The real work was to get five different teams to adopt it. Each team owned a part of the delivery pipeline.

They had different timelines, SLAs, and priorities. Each team had its own local optimizations for "when content gets updated." No one wanted to own global coordination, because each team thought that another team already did.

First, we had to earn trust that the event system was stable and would not cause regressions. We documented and promoted the contract shape and the meaning of each event. We paired with teams to connect listeners and verify real-time invalidations. We also created visibility with dashboards and shared alerts, so all teams saw the same “truth” when content changed.

At first, some teams had doubts. But then they could trace an event to a cache purge within seconds and see the result in production. After that, they agreed.

The turning point was to make the system easy to adopt and hard to ignore. The result was faster systems and faster alignment.

## Coordinate caches instead of removing them

This project did not remove caching. It coordinated caching.

Teams often use crude methods for cache invalidation: lower TTLs, purge everything, or hope that the client refreshes. At scale, these methods are not sustainable or necessary.

Event-driven coordination let us keep the layers that made our platform fast. Content publishing became a signal for the full system. It reliably coordinated freshness across a distributed network of services.

The best architectures solve the problem that you intended to solve. They also show you problems that you did not know you had.

For us, cache invalidation gave teams a shared vocabulary. A system that started as a fix for staleness became a platform for trust, between services and between the people who build them.
