Every application needs access to something: a secret store, a configuration service, a database, a file share. The easiest way to grant that access is a connection string or an access key. It works on the first try, and it creates problems for years.

A shared key is a bearer credential. Possession is authorization. Every operational problem with shared keys comes from that one property.

Rotation affects the whole fleet. When you rotate a resource key, every application that uses it breaks at the same moment. So teams postpone rotation, which is the wrong outcome for a credential.

Access has no name. The audit log shows that someone used the key, but never which application used it. Tracing an access back to a workload becomes guesswork.

Scope is all or nothing. Anyone with the key gets everything that the resource offers. A connection string cannot express least privilege.

## The doctrine

The rule that fixes this is short. In the cloud, applications authenticate only as managed identities, so there is no secret to leak, rotate, or distribute. Where that is physically impossible, the fallback is the smallest possible secret, never a resource key.

That second sentence matters as much as the first. A doctrine with no exception process tends to fail quietly, one undocumented workaround at a time. A doctrine that names its exception and keeps that exception small can survive contact with real systems.

## A chain of short-lived proofs

In Kubernetes, workload identity federation replaces stored credentials with a chain of proofs. The system mints each link on demand, and each link expires on its own.

The kubelet projects a short-lived OIDC token into the pod. That token only states which service account the pod runs as. It is not a credential for any resource. Entra ID trusts the cluster's OIDC issuer for that service account subject, and exchanges the token for an access token that belongs to the application's user-assigned managed identity. That access token is short-lived, and its scope is exactly the role assignments of that identity. The resource checks those role assignments and logs the access with the identity's name.

If the access token leaks, the exposure is one identity's grants for a few minutes. If a storage key leaks, the exposure is everything that the storage account offers, until a human rotates the key and breaks every consumer in the process.

The wiring is small. The chart binds the service account to the identity:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: reporting
  annotations:
    azure.workload.identity/client-id: '00000000-0000-0000-0000-000000000000'
```

The application names its identity in configuration, and the Azure SDK does the rest. No secret appears anywhere in the path.

## Grants live with the identity

One structural choice makes this model auditable. The infrastructure module that creates an application's managed identity also declares every role assignment for that identity. That one file is the complete, peer-reviewed answer to "what can this application access?"

In the world of connection strings, that question needed a tour of every resource's access settings, and even then it could not say which application used which key. When grants follow the identity in code, the question becomes a file read and the answer goes through code review.

## The exception: a smaller secret, not a bigger key

Real platforms have places where federation does not work. A common example is workloads in a private data center that cannot use federated credentials at all. The decision there was between keeping the existing resource connection strings or replacing them with service principals that use a client secret.

Keeping connection strings was simpler, because they already existed. It also kept every problem: broad access after a leak, no isolation between applications that share a key, fleet-wide rotation, and nothing in infrastructure code for anyone to review.

Service principals were chosen. One client secret per application replaces a set of broad resource keys. Each application has its own identity, so access is isolated and attributable, and its grants live in reviewed infrastructure code. The client secret lives in a key vault. The migration path also ends itself. When the last workload leaves the private data center, the code path that uses secrets can be deleted and the work is done.

The cost is honest. At least one class of secret still needs rotation, and two authentication strategies need maintenance until the exception ends. The platform carries that secret on purpose, because it is small, it rotates in one place, and it is already scheduled for deletion.

## The decision, in code

The whole decision, including the doctrine, the exception, and the local developer experience, fits in one method of the shared service library:

```csharp
private ITokenCredentialFactory ChooseStrategy()
{
    var info = ServiceInfo.From(_configuration);
    if (info.UseManagedIdentity)
    {
        return info.UsePersonalIdentity
            ? new LocalDeveloperCredentialFactory()
            : new ManagedIdentityCredentialFactory(info);
    }
    return new LegacyServicePrincipalCredentialFactory(_configuration);
}
```

In the cloud, the managed identity strategy uses `DefaultAzureCredential` pinned to the application's identity, and there is no secret anywhere. In the legacy environment, the service principal strategy uses a client secret read from the vault. On a laptop, the developer strategy uses plain `DefaultAzureCredential`, so after `az login` a developer runs the same code path as the cluster with their own identity.

When the exception ends, its removal is a code deletion, not a migration. The legacy branch goes away, along with the one secret it reads. Shaping the code so that the exception can be deleted cleanly is what makes the promise of "temporary" believable.

## Every credential is one of a few classes

The same principle extends past application-to-cloud access. The pattern is always the smallest identity that can hold the grant, with a stored secret only where a protocol requires one.

Managed identity with workload identity federation is the default for every cluster workload, with no stored secrets. Legacy service principals cover the one deliberate exception. CI pipelines authenticate to their own build platform with a short-lived Entra token from a service principal instead of an ambient, broadly scoped pipeline token, and the same script runs on a laptop after `az login`. Source control hosts that have no managed identity get a GitHub App, which turns a private key into a signed JWT and then into a one-hour installation token. Some data plane protocols, such as certain message brokers and databases, cannot use Entra at all. There, the credential is a client certificate for mutual TLS that cert-manager issues and rotates inside the cluster. It still has no password, and it still names the client.

Resource keys and connection strings are the class the doctrine exists to remove. Any remaining instance is a finding, not a pattern.

A companion rule keeps the residual secrets in one place. The secrets that do remain live only in a key vault, and the configuration service references them. They never appear in code, pipelines, or source control. Identity is how you avoid secrets, and the vault is where the unavoidable ones go.

## Keeping the exception small

The exception will try to grow. Once a code path that reads a client secret exists, it becomes the easiest answer to the next hard integration. Every new use of the legacy strategy should be treated as a design question, and the number of applications on that path should only go down.

Audit the audit file. The claim that one module file holds every grant for an identity is only true if nobody adds role assignments elsewhere, for example through a portal or in another module. A periodic comparison between declared and actual role assignments keeps the claim honest.

Watch the federated credential subjects. The safety of workload identity depends on the exact match between the cluster issuer, the namespace, and the service account name. A loose or reused subject lets the wrong workload become the right identity.

Remember the developer experience too. The local strategy is not a convenience bolted on afterward. It is why developers do not reach for a personal access key when something fails on their laptop. If the secure path is also the path that works locally, people stay on it.
