I do not like to give all my site analytics to Google. So I decided to self-host [Plausible Analytics](https://plausible.io/). The goal was more than tracking page views. I wanted to own my data, learn more about the infrastructure, and test a modern, privacy-first approach.

My portfolio site already ran as an Azure Static Web App behind Azure Front Door. I decided to over-engineer the analytics a little, to see what was possible. This post shows how I did it.

## The Setup

An Azure Kubernetes Service (AKS) cluster hosts everything. I created the cluster with Terraform, but this post does not include the scripts. Use the tool you prefer: Bicep, the Azure CLI, or your own Terraform. The AKS cluster must support Workload Identity, have access to an Azure DNS zone, and be reachable behind Azure Front Door.

I installed NGINX as my ingress controller with Helm. I added only two special values. They make sure that it keeps client IPs and watches all namespaces:

```bash
helm upgrade ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --set controller.service.externalTrafficPolicy=Local \
  --set controller.watchNamespace=""
```

The result was an ingress controller with a public IP that could sit behind Front Door.

## TLS Done Right (and Automatically)

My favorite part of this project: cert-manager issues and renews TLS certificates automatically, with no stored secrets. A DNS-01 ACME challenge and Azure Workload Identity make this possible.

The more common HTTP-01 challenge needs special routing and path-based verification. DNS-01 is different. With DNS-01, cert-manager creates TXT records in your Azure DNS zone. Let’s Encrypt can then verify domain ownership without access to your app.

The high-level setup:

- I created a `ClusterIssuer` resource in Kubernetes that used the DNS-01 method
- I gave cert-manager a managed identity with **DNS Zone Contributor** permissions
- I stored no client secrets or keys. cert-manager used Azure identity for everything

After that, cert-manager automatically issued a wildcard certificate for `*.walkersmith.me`. It has renewed the certificate with no problems since then.

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: X
    privateKeySecretRef:
      name: letsencrypt-prod
    solvers:
      - dns01:
          azureDNS:
            managedIdentity:
              clientID: XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
            subscriptionID: XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX
            resourceGroupName: X
            hostedZoneName: walkersmith.me
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: wildcard-walkersmith-me
  namespace: plausible
spec:
  secretName: wildcard-walkersmith-me-tls
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  commonName: '*.walkersmith.me'
  dnsNames:
    - '*.walkersmith.me'
    - walkersmith.me
  usages:
    - digital signature
    - key encipherment
    - server auth
  renewBefore: 24h
```

## Deploying Plausible with Helm

Plausible supplies a Docker Compose setup that you can adapt for Kubernetes. I decided to put everything in a Helm chart instead. The chart deployed:

- The Plausible app
- Clickhouse (for event storage)
- PostgreSQL (for configuration and auth)

All three used persistent volume claims, so pod restarts or upgrades do not lose data. Each component had its own PVC, templated in Helm as follows:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: {{ $fullname }}-db-data
  namespace: {{ .Values.namespace }}
spec:
  accessModes:
    - {{ .Values.persistence.accessMode }}
  resources:
    requests:
      storage: {{ .Values.persistence.size }}
```

The chart has similar claims for the Plausible app (`plausible-data`), Clickhouse events (`event-data`), and logs (`event-logs`). If you plan to self-host Plausible for any length of time, persist your data. Do not skip this step.

A login protects the dashboard, as in the hosted Plausible service. It works out of the box.

## Ingress, Meet Front Door

After the app was live in the cluster, I exposed it with an Ingress resource. The Ingress had a host rule for `analytics.walkersmith.me`. Because of cert-manager, that endpoint already had valid HTTPS and worked in the browser.

But my static site did not send traffic directly to the AKS ingress. The site was behind Azure Front Door.

I wanted only Azure Front Door to reach the cluster, so I restricted ingress traffic at the network layer. A Kubernetes `NetworkPolicy` and an Azure NSG (Network Security Group) allow traffic only from the known Front Door IP ranges. This blocks direct access to the public IP of the ingress controller. Analytics traffic can use only the intended entry point.

Then I configured a Front Door origin as follows:

- **Origin type:** Custom
- **Hostname:** `plausible.walkersmith.me`
- **Origin host header:** `analytics.walkersmith.me`
- **Certificate subject name validation:** Enabled

With this origin, Front Door sent traffic to the AKS ingress based on the host header, and everything worked. Each request went to Front Door, then to the cluster. The TLS certificate from cert-manager secured the connection.

If you know Front Door, you know this pattern. You build a host-based router with multiple origins. It puts multiple backend services under one domain. Here, `walkersmith.me` serves my static site, and the analytics are at `analytics.walkersmith.me`.

## Bringing Analytics to the Site

With the infrastructure in place, it was easy to add Plausible to the site. Put the JavaScript snippet in the HTML:

```html
<script
  defer
  data-domain="walkersmith.me"
  src="https://analytics.walkersmith.me/js/plausible.js"
></script>
```

Plausible is at `analytics.walkersmith.me`, and my static site is at `walkersmith.me`. So the `data-domain` value is the value that Plausible expects.

Traffic goes from the browser → Azure Front Door → AKS ingress → Plausible app. I get all the statistics, and no user data goes to third parties.

## Closing Thoughts

This project was too much for a personal portfolio, but that was the point. I wanted to see a clean, modern, and secure analytics stack, with automation at every step and no secrets to manage.

If you run your own site, this approach is more work than Google Analytics. But it gives you control, privacy, and confidence. Your data stays yours, and no third party receives your traffic data.

It is also satisfying to see statistics come in from a system that you fully own. It runs behind a global CDN on a production-grade cluster, secured by cert-manager, with no secrets.
