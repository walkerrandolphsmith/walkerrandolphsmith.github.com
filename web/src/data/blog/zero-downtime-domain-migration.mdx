I moved this site from `walkerrandolphsmith.com` to `walkersmith.me` with zero downtime. Every old link still lands on the same page, every request uses HTTPS, and search ranking did not drop. The order of the work made that possible, more than any single tool.

## Why the domain changed

I used `walkerrandolphsmith.com` for more than ten years. The name was long, hard to spell, and easy to forget. The new domain, `walkersmith.me`, is shorter and matches my personal brand.

A domain change puts three things at risk. The site can go down during the switch. Search engines can see two copies of the same content and lower its ranking. Links that other people already use can break. The migration had to protect availability, search ranking, and every existing link at the same time.

## The new domain started outside Azure

Azure Static Web Apps hosts the site. I managed the old domain through App Service Domains and an Azure DNS zone. App Service Domains does not support the `.me` top-level domain, so I bought `walkersmith.me` through GoDaddy. The new domain therefore started at a different registrar and outside Azure DNS.

## Why Front Door sits in front of both domains

The simplest option was to point the apex (`@`) of the new domain at the static IP address of the Static Web App. I rejected it for two reasons. Traffic would bypass Azure Front Door, so the site would lose the performance and security of a global edge. Both domains would also serve the same content, and duplicate content is a large search ranking risk.

I chose to put Azure Front Door in front of both domains. Front Door holds the HTTPS certificate for each custom domain and serves the site from its global edge. It also redirects the old domain to the new one. One entry point then controls every request, so certificates and redirects live in one place. I managed the Front Door profile, the DNS zones, and the redirect rules with Terraform.

## Each risk and its control

### Separate the edge change from the domain change

I moved the old domain behind Front Door before I touched the new domain. I created a Front Door profile and added `walkerrandolphsmith.com` and `www.walkerrandolphsmith.com` as custom domains. Front Door verified ownership and issued the TLS certificates. In the Azure DNS zone, an alias A record points the apex at the Front Door endpoint, and a CNAME record points `www` at it.

After this step, all traffic to the old domain already went through Front Door. If anything had failed, the failure would have belonged to one change, not two.

### Make the new domain ready before delegation

The riskiest moment was the switch of name servers at GoDaddy. If Azure DNS or Front Door was not ready for `walkersmith.me` at that moment, the new domain would fail. So I built and checked everything first.

I created an Azure DNS zone for `walkersmith.me` and added the apex and `www` as custom domains in Front Door. I completed domain validation and waited for the HTTPS certificates. The new zone got the same records as the old one. An alias A record points the apex and a CNAME record points `www` at the same Front Door endpoint.

Before I made the change live, I queried the authoritative Azure name servers directly, with commands such as `nslookup -type=CNAME walkersmith.me ns1-08.azure-dns.com`. Each record resolved correctly. Only then did I update the name servers at GoDaddy. Front Door could serve the new domain as soon as GoDaddy delegated authority to Azure.

Name server changes can take up to 48 hours, but they usually propagate within an hour. The timing did not matter here. The old domain already ran through Front Door, and the new domain was ready to serve as soon as each resolver picked up the delegation.

During the cutover, I watched traffic in Plausible Analytics and in a Log Analytics workspace.

### Keep every existing link working

A rule set named `redirect-legacy` in Front Door matches requests where the `Host` is `walkerrandolphsmith.com` or `www.walkerrandolphsmith.com`. It returns a 301 redirect to the same path on `walkersmith.me`. Because the rule keeps the path, deep links such as `/blog` and `/about` reach the same page, not only the homepage. A 301 marks the move as permanent for browsers and search engines.

### Protect search ranking

Each page also declares its primary URL. In the Next.js app, page metadata adds a `<link rel="canonical">` tag to every page:

```ts
export const metadata = genPageMetadata({
  title: 'Blog',
  canonical: 'https://walkersmith.me/blog',
})
```

The canonical tag tells search engines which URL is the primary copy of the content. They then do not index the same content twice under two domains.

## Checking the result from the command line

I checked the result with two commands:

1. `nslookup walkersmith.me` shows the Azure DNS name servers.
2. `curl -I -L -v http://walkerrandolphsmith.com/blog` shows the redirect chain. A 307 redirect moves HTTP to HTTPS, a 301 redirect goes to `walkersmith.me/blog`, and the new domain returns 200.

I announced the move on social media and noted that the old domain still redirects automatically.

## What the result proved

The site had no downtime, every old link redirects to the same page on the new domain, and every request uses HTTPS. Search ranking did not drop.

The order of the work is what made the move safe. Move the edge first, so that the domain change is the only change left. Build and verify the new domain before you delegate it. Keep certificates and redirects at one entry point, so that one rule set protects every link.
