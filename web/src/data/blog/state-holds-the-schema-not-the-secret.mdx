Another in a collection of posts about designs the constraints chose for us. The constraint here is a brutal reality of Infrastructure as Code that usually takes a security audit to fully internalize: **a Terraform state file is fundamentally a plaintext document.** You can encrypt the backend storage bucket, you can lock down the RBAC, but at the end of the day, any principal or CI runner that executes a `terraform plan` must be able to read the state. If you put a database password or a third-party API key into an `azurerm_key_vault_secret` value, it is written to that state file. You haven't secured the secret; you've just moved the leak.

The industry's reflex to this constraint is terrible. Teams decide that because Terraform can't securely hold the *value*, Terraform shouldn't manage the secret at all. They drop back to "ClickOps"—someone logs into the Azure Portal, creates a secret by hand, and pastes the value in.

That solves the state leak, and creates three worse problems:

1. **No auditability:** There is no single source of truth for what secrets an environment requires.
2. **Disaster recovery is a guessing game:** If the vault is deleted, there is no code to recreate the keys. You only find out what's missing when microservices start crashing.
3. **No peer review:** A developer can add a new external dependency without it ever passing through a Pull Request.

The instinct to separate the secret from the code was correct. The mistake was treating the secret as a single indivisible object.

## The Reframe: The Shell is the Contract

A secret in a Key Vault is actually two things: a **schema** (the name of the key, its tags, the fact that it exists) and the **data** (the cryptographic bytes).

> The schema is infrastructure. The data is state. You manage the infrastructure in code; you manage the state out of band.

And this is an interface narrative through and through — the same shape I [argued for with certificates](/blog/the-certificate-is-an-interface), now pointed at a vault. The `locals` block isn't just an array of strings. It is the explicit, code-reviewed contract of every external credential your platform consumes.

```hcl
locals {
  unmanaged_secret_placeholder = "XXXXXXX"

  # This array is the API surface of your environment's external dependencies.
  unmanaged_secrets = toset([
    "StaticSecretToExternalSystem",
    "StripeApiKey",
    "SendGridToken"
  ])
}
```

When a developer needs to integrate a new third-party vendor, they don't submit a Jira ticket to an operator to "please create a secret." They submit a PR modifying this `unmanaged_secrets` array. The PR is the audit trail. It forces the conversation: *Why do we need this? What is the rotation policy? Whose budget is paying for this?*

## The Mechanics: Asserting Existence Without Capturing State

The execution relies on a specific Terraform primitive that is often misused for hacky workarounds, but here finds its architectural purpose: `ignore_changes`.

```hcl
resource "azurerm_key_vault_secret" "unmanaged" {
  for_each = local.unmanaged_secrets

  name         = each.key
  value        = local.unmanaged_secret_placeholder
  key_vault_id = azurerm_key_vault.vault.id

  tags = {
    environment   = module.common.environment
    file-encoding = "utf-8"
    managed-by    = "terraform"
    description   = "Topology managed by IaC. Value managed out-of-band."
  }

  lifecycle {
    ignore_changes = [value]
  }
}
```

Here is exactly what happens when this applies to a fresh environment:

1. Terraform creates the secret with the name `StaticSecretToExternalSystem`.
2. It writes the dummy value `"XXXXXXX"`.
3. An authorized human or a dedicated secret-injection pipeline updates the value in Key Vault to the real, sensitive bytes.
4. On the *next* `terraform plan`, Terraform queries the Key Vault API, sees that the value is different from `"XXXXXXX"`, but because of `ignore_changes = [value]`, it **ignores the drift**.

Terraform asserts the *existence* of the secret, but relinquishes custody of the *content*. You get an environment that physically cannot be deployed without explicitly documenting its dependencies, and a state file that contains nothing but `"XXXXXXX"`.

## The Honest Edges

This pattern is the position I'd defend in front of any auditor, but it introduces operational friction you have to account for.

* **The Bootstrapping Race Condition:** When you stand up a new environment from scratch, Terraform provisions the vault and fills it with dummy values. If your microservices boot immediately after Terraform finishes, they will pull `"XXXXXXX"` and crash. You have introduced a mandatory, out-of-band operational step between "infrastructure applied" and "applications ready."
* **Accidental Deletion Recovery:** If someone manually deletes the secret in the Azure Portal, the next Terraform run *will* catch the missing resource and recreate it—but it will recreate it with `"XXXXXXX"`. The app stays broken until the real value is manually restored.
* **Rotation is Blind:** Terraform knows nothing about the lifecycle of the actual credential. If the `StripeApiKey` expires in 30 days, your IaC provides zero help. This pattern solves the *topology* problem, but you still need an operational process for secret rotation — the [lifespan dial](/blog/its-not-where-the-secret-lives) lives entirely outside this design.

## The Takeaway

This isn't low-level plumbing; it is the boundary line between your infrastructure plane and your security plane.

1. **State files leak by design.** Never put cryptographic material in an `azurerm_key_vault_secret` value unless you want it sitting in plaintext in Azure Blob Storage.
2. **ClickOps is not an audit trail.** Manually creating secrets hides your system's external dependencies from code review and destroys your disaster recovery posture.
3. **Separate the schema from the data.** Define the list of required secrets in code. That array is the strict interface of your environment's dependencies.
4. **Use `ignore_changes` as a custody transfer.** Let Terraform create the shell with a dummy value, and explicitly tell it to ignore whatever a human or secure pipeline injects later.
5. **Accept the bootstrapping tax.** Your environment creation now requires an out-of-band step to populate the real values. That is the price of keeping your state file clean.

Define the contract in code. Inject the bytes in the dark.

_If you're using this pattern, how are you handling the bootstrapping race condition — do your deployment pipelines pause for a human to inject the values, or do you have a secondary automated system that handles the population?
